## Вывод о переиспользовании

Переписывать библиотеку целиком не требуется. Математические алгоритмы преобразования матриц, Дирихле и операций над графами уже реализованы. Формальная алгебра также содержит значительную часть нужных правил и ценные проверки ориентации. Однако нынешний численный матричный слой и округляющая коэффициенты алгебра не являются точным эталонным ядром. Обёртки с новыми именами этого не исправят.

Сохраняем публичные классы и импорты. Сначала исправляем локальные дефекты, затем выделяем внутренние механизмы арифметики и контекстов, после этого добавляем строгий интерфейс. Старый интерфейс адаптируем к общим механизмам; две независимые реализации одинаковых математических правил поддерживать не следует.

## Сопоставление всех операций ТЗ

«Переиспользовать» означает сохранить алгоритм после проверки нового контракта; это не обещание перенести функцию без изменений.

| Требование | Текущая опора | Необходимая работа |
| --- | --- | --- |
| C01: сеть из рёбер | `Polyform.from_networkx`, `from_pairs`, `matrix/networkx.py` | Новый независимый от NetworkX объект сети: явные вершины, изоляты, компоненты, точные веса, политика кратных рёбер. Переиспользовать правила проверки входов |
| C02: сеть из L | `Polyform.from_laplacian`, `Laplacian`, `_numeric.validate_laplacian` | Объединить проверки, добавить точную ветвь и диагностику допустимых численных коррекций |
| C03: сеть из R | `_numeric.validate_resistance`, `MatrixOperations.to_laplacian` | Сохранить двойное центрирование и блочный подход; перепроверить ранг, знаки восстановленной L, точную арифметику и отказ при неопределённости |
| C04: перестановка | `LabeledMatrix.reordered`, `Basis.reordered` | Переиспользовать правила порядка; распространить на сеть и координаты, сохранить неизменность исходного объекта |
| C05: численный перевод | `LabeledMatrix` приводит данные к численному представлению | Новый явный переход с проверкой переполнения и исчезновения ненулевых значений |
| M01: L | `Polyform.to_matrix`, адаптер NetworkX, `Laplacian` | Общая сборка из проводимостей для двух режимов, без обязательного построения полиформы |
| M02: Gr | `MatrixOperations.to_greenian`, `_blockwise`, `_numeric.pinv` | Сохранить разбиение; исправить масштабирование и передачу компонент, добавить точное блочное решение |
| M03: R | `MatrixOperations.to_resistance`, `_numeric.distance` | Переиспользовать формулу; исправить ложную бесконечность, добавить вычисление выбранных пар и точный режим |
| M04: остовной вес | `Laplacian._tree_geometry`, `Polyform._spanning_form`, `potential` | Отдельный публичный кофакторный расчёт без сферы/экспоненты; exact, пустой граф, изоляты и компонентные ответы |

| G03: произведение внешних структур | `Simplex`, `Polysimplex` | Новый прямой детерминант Gram; переиспользовать ориентационные соглашения и проверки грейда |
| G04: объём | Геометрические примеры и формы симплексов | Новый явный интерфейс с нормировкой `(k!)²`, проверкой связности и особых размерностей |
| D01: Дирихле | `Laplacian.dirichlet`, `DirichletResult` | Переиспользовать выбор блоков и условия единственности; добавить exact и новый контекст |
| D02: продолжение | `DirichletResult.extend` | Переиспользовать умножение на H; строгие метки, режимы, диагностика |
| D03: редукция Крона | `Laplacian.eliminate`, `EliminationResult` | Переиспользовать дополнение Шура; exact, согласованный результат сети и H |
| D04: стягивание | `Laplacian.contract`, `ContractionResult` | Переиспользовать разбиение и матрицу принадлежности; проверять сохранность слабых внешних связей при больших внутренних весах |
| D05: индуцированный подграф | `Laplacian.induced_subgraph` | Переиспользовать пересборку диагоналей; exact, пустой выбор, изоляты |
| A01: внешнее произведение | `Simplex`, `Polysimplex`, `Monoid` | Сохранить ориентационные правила; исправить компактное слияние, отделить коэффициенты от округления |
| A02: граница | `Element.boundary`, `Simplex.boundary`, `Polysimplex.boundary` | Сохранить линейность и знаки; явный функционал ε и точная координатная ветвь |
| A03: выделение грейда | `LinearCombination.extract_grade`, `Polyform.extract_grade` | Переиспользовать с сохранением контекста и рациональных коэффициентов |
| A04: квадрат поддерживаемого терма | `quForm`, `Simplex.to_polyform` | Строго проверить грамматику; не вводить квадрат произвольной суммы |
| A05: произведение форм | `quForm`, `Polyform`, общий механизм умножения | Переиспользовать правила, убрать потери коэффициентов в точном режиме |
| A06: эквивалентность | `Polyform.is_equivalent` | Сохранить внутренние пары координатных коэффициентов; exact-сравнение и лимит раскрытия. Общие билинейные формы публично не добавлять |
| A07: полярная форма | `Polyform.polar_form` | Сохранить алгоритм первого грейда, проверить нормировку и явный отказ в остальных случаях |
| A08: экспонента | `Polyform.exp`, `LinearCombination.exp` | Сохранить конечное разложение; точные факториалы, нулевой скалярный член, лимиты промежуточного роста |

| A11: потенциал | `Polyform.potential` | Переиспользовать `τ(MF)`, убрать эвристику для нового строгого интерфейса |
| A12: оценка формы | `Polyform.norm`, `potential`, матричный слой | Новый связующий алгоритм: Gram или нормированный потенциал; не строить полную экспоненту для каждого запроса |

## Общие механизмы: что действительно потребуется написать

- Рациональный вычислительный слой: сейчас матрицы используют float64, а `_core/lincomb.py` округляет и удаляет малые коэффициенты. Проверить также скалярные операторы `Element`, `Simplex`, `quForm`, деление и факториалы: изменение одного `_finalize` недостаточно.
- Неизменяемые контексты, идентичность, порядок меток и режим арифметики. `Space`, `Basis`, `MatrixAxis` дают отправную точку, но изменяемые элементы и базисы требуют совместимого перехода.
- Общие типы результата и ошибок, численная политика, нормированные невязки и оценка обусловленности. Нынешние `ValueError` и результаты в `matrix/results.py` можно адаптировать, но единого контракта ТЗ пока нет.
- Проверка ресурсов для раскрытий и вычислений; сериализуемая запись результата для агента. Сам агент, сервер и пользовательский интерфейс сюда не входят.

NumPy оставить численным исполнителем, SymPy добавить для точных матриц. NetworkX постепенно вынести в необязательный адаптер: он сейчас импортируется и из `combinations/polyform.py`, поэтому одного изменения зависимостей недостаточно. pandas оставить необязательным; SciPy не вводить до задач разреженных сетей. Версии Python 3.12/3.13 из ТЗ — предложение будущей матрицы проверки, не уже принятое прекращение поддержки объявленного Python ≥3.8.

## Первый этап исправлений

1. **Ложное разбиение сети при обращении Gr.** В `_numeric.validate_greenian` обратное преобразование и определение компонент применяют абсолютный порог, непригодный одновременно для L и Gr. Для ребра проводимости `10¹²` получается бесконечное сопротивление вместо `10⁻¹²`. Сохранять топологию исходной сети, нормировать компонентные задачи, независимо проверять численный ранг. Для внешней Gr без известной топологии нужен отдельный проверяемый путь восстановления, а не доверие метаданным. Простая глобальная замена `atol` на ноль недостаточна. При неразрешимости — явная ошибка, не ложная несвязность. Приёмка: T28, T32, преобразования L→Gr→R на нескольких масштабах, включая несвязные сети.
2. **Слияние границ с неединичным ε.** `Simplex._full_normalize` применяет правило для единичных аффинных весов к более широкому входу. При весе общей вершины 2 теряется множитель 2. В компактной записи первой версии разрешить только ε=1; остальные данные отклонять до слияния. Общую границу вычислять координатно. Приёмка: T20–T21, T30; сравнение с прямым раскрытием и прежние ориентационные тесты.
3. **Исчезновение точных малых коэффициентов.** Это отдельная системная задача точной арифметики, а не маленькая правка допуска. Вынести в этап точного слоя; обязательная регрессия T29. Старое приближённое поведение не переносить в новый exact-интерфейс.

Ошибки повторно локализованы чтением текущего кода. Численные воспроизведения и 480 успешно пройденных тестов относятся к ревизии указанного коммита; в текущем документальном этапе тесты повторно не запускались.

## Версия библиотеки

Сейчас `pyproject.toml` содержит `version = "0.2.0"`. В публичном `polyform_algebra/__init__.py` нет `__version__` или функции получения версии.

Предлагаемый контракт: `polyform_algebra.get_version() -> str`, а также привычный `polyform_algebra.__version__`; оба возвращают одинаковую версию установленной библиотеки. Единственный редактируемый источник — `[project].version` в `pyproject.toml`. Получать установленную версию через стандартный `importlib.metadata.version("polyform_algebra")`; не добавлять вторую строковую константу версии. Для разработки использовать editable-установку, после изменения metadata переустанавливать пакет. Поведение прямого запуска из неустановленного checkout определить явно: функция сообщает `PackageNotFoundError`, сам импорт математических классов остаётся доступным; доступ к `__version__` можно сделать ленивым. Не подставлять молча `0.0.0`.

Проверки: равенство функции, атрибута и metadata установленного wheel; editable-установка; отсутствие установки в изолированном окружении; чтение версии вне checkout. Чужая ранее установленная копия не должна маскировать проверяемую сборку. Версию пакета и ревизию математических определений хранить раздельно.

Политика: исправления совместимого поведения — patch (`0.2.1` как кандидат первого исправляющего выпуска); новые публичные возможности — minor; несовместимые изменения — отдельный документированный переход. Не повышать версию за каждую правку текста. Точный номер следующего выпуска назначать по фактическому составу изменений; здесь `0.2.0` не меняется. Релиз в публичный реестр — только по отдельному запросу.

## Ядро и тематические расширения

В ядре остаются только функции ТЗ и их общие механизмы. Из нынешнего `Laplacian` сфера, центральности, аннигиляторы для направленных задач и балансировка относятся к расширениям. Двудольные преобразования, спектральные переходы, общая геометрия `Space`/`Basis` и исследовательские примеры также не являются условием готовности минимального ядра.

Это не основание удалять существующие возможности. Сначала отделить внутренние зависимости, затем при необходимости переместить реализацию за совместимыми методами старого API. Расширения зависят от ядра, обратных импортов нет. Старые тематические тесты продолжают проверять совместимость; они не заменяют обязательные проверки нового контракта.

Оценивать готовность следует по таблице операций и критериям приёмки, а не по проценту повторно использованных строк. Основной объём новой работы сосредоточен в числовом контракте и проверках; математические формулы и значительную часть существующих алгоритмов можно сохранить.
