# Ревизия программного кода PMG и состав эталонного ядра

**Дата:** 8 ноября 2026 года. **Статус:** аналитический отчёт и предложение по архитектуре. Исходные файлы проектов не изменялись.

**Вывод:** PMG нужна небольшая проверенная вычислительная библиотека поверх существующих математических инструментов. Её ценность — в точном выполнении соглашений PMG, воспроизводимости и обнаружении недопустимых вычислений. Развивать собственную универсальную систему символьной и численной математики оснований нет. Разовые исследования, построение рисунков и большинство специальных формул можно оставлять ИИ и обычным Python-скриптам.

Существующую `polyform_algebra` стоит сохранить и сузить её публичные обещания. В ней уже есть полезные предметные проверки и содержательные тесты. Однако в нынешнем состоянии её нельзя объявлять эталоном всей актуальной PMG: формальная модель намеренно ограничена, точная арифметика не поддерживается последовательно, а дополнительные проверки обнаружили ошибки за пределами штатных тестовых примеров.

## Что показывает существующая практика исследований

Ни в пяти скриптах основного репозитория, ни в 119 файлах `pmg-notes/checks` не обнаружено прямого импорта `polyform_algebra`. В последнем корпусе 58 файлов импортируют `fractions`, 19 — SymPy, 8 — NumPy; группы пересекаются. Здесь есть также рисунки, переводы и служебные программы, поэтому число 119 не означает 119 самостоятельных математических алгоритмов.

Следовательно, публичные исследования уже имеют вычислительный путь, независимый от устанавливаемой библиотеки. Это подтверждает заменимость большого числа конкретных расчётов обычным Python. Оно не доказывает, что библиотека не используется вне исследованных репозиториев, и не измеряет надёжность произвольного ИИ.

При этом в проверочных скриптах повторяются собственные `determinant`, `inverse`, `laplacian`, умножение матриц, полиномиальная арифметика и перебор лесов. Например, [проверка дуальности](https://github.com/magin67/pmg-notes/blob/9bbd84fe7a40292da6780bc4491f15ba2b3e318e/checks/dual/verify_vector.py) содержит рациональное обращение матриц и внешнюю алгебру, а [проверка лесных степенных сумм](https://github.com/magin67/pmg-notes/blob/9bbd84fe7a40292da6780bc4491f15ba2b3e318e/checks/matroid/verify_forest_power_sums.py) — ещё один набор матричных операций. Часть этой независимости полезна: она позволяет проверять один результат разными способами. Превращать все такие реализации в постоянный публичный API нецелесообразно.

Нужны два разных актива: **удобное ядро для повторного использования** и **корпус независимых эталонных примеров**. Если все проверки начнут вызывать тот же алгоритм ядра, независимость проверки будет потеряна.

Версия пакета — `0.2.0`. `requirements.txt` корректно отсылает к `.[dev]`, а не содержит второй независимый список. pandas импортируется дополнительными адаптерами; SymPy и SciPy зависимостями пакета не являются.

Проверка выполнена на Python 3.12.1, NumPy 1.26.3, NetworkX 3.6.1, SymPy 1.14.0, pandas 2.1.4 и pytest 9.0.3. SciPy в данном окружении отсутствует. В проверенном дереве Python-репозитория нет собственного workflow `.github` для непрерывной проверки.

Большая часть численной математики в пакете **уже делегирована NumPy**. Поэтому «заменить библиотеку на NumPy» часто означает убрать полезные проверки вокруг тех же решателей, а не избавиться от собственного сложного алгоритма.

### Ошибка масштаба при переходе от лапласиана к сопротивлениям

Для единственного ребра проводимости `10¹²` верный резистенс равен `10⁻¹²`. При стандартных допусках библиотека возвращает `+∞`.

```python
import networkx as nx
from polyform_algebra.matrix.networkx import from_networkx

g = nx.Graph()
g.add_edge("a", "b", weight=1e12)
lap = from_networkx(g)
lap.to_resistance().to_numpy()   # вне диагонали получается inf
```

Причина установлена: исходный лапласиан имеет одну компоненту, но при валидации малого по масштабу гриниана повторное псевдообращение с тем же абсолютным порогом обнуляет значимые сингулярные значения. Гриниан получает две компоненты, и следующее преобразование заполняет межкомпонентные значения бесконечностями. [Валидация гриниана](https://github.com/magin67/polyform_algebra/blob/6e5da8dd14265ef67a0ed472344187ad28207317/polyform_algebra/matrix/_numeric.py#L111), [переход к сопротивлению](https://github.com/magin67/polyform_algebra/blob/6e5da8dd14265ef67a0ed472344187ad28207317/polyform_algebra/matrix/_operations.py#L215).

С `MatrixTolerance(atol=0)` этот конкретный пример даёт правильный результат. Это диагностическая проверка, а не универсальная рекомендация отключить абсолютную погрешность. Эталон должен сохранять сведения о связности и либо вычислять результат при согласованном масштабе, либо явно сообщать о численной неразрешённости. Молчаливое изменение связности недопустимо. Приоритет исправления — высокий перед использованием агентом.

### Компактные границы принимают более широкие входы, чем допускает правило слияния

Вход с весами `ε(a)=1`, `ε(b)=2`, `ε(c)=1` принимается конструктором. Однако произведение компактных границ `(ab)(bc)` после раскрытия отличается вдвое от произведения отдельно раскрытых границ:

```text
Компактное слияние:  [bc] − 2[ac] + [ab]
Прямое раскрытие:  2[bc] − 4[ac] + 2[ab]
```

По правилу Лейбница здесь должен присутствовать множитель `ε(b)=2`. Сокращённое правило без этого множителя обосновано для соответствующих базовых вершин веса 1, но реализация не ограничивает вход этой областью. [Слияние факторов](https://github.com/magin67/polyform_algebra/blob/6e5da8dd14265ef67a0ed472344187ad28207317/polyform_algebra/objects/simplex.py#L107), [граница через аффинный вес](https://github.com/magin67/polyform_algebra/blob/6e5da8dd14265ef67a0ed472344187ad28207317/polyform_algebra/objects/simplex.py#L251).

Минимальное безопасное решение при последующей разработке — явно ограничить компактные сокращения допустимыми атомами, а в других случаях раскрывать координаты или отказывать. Это не требует расширять публичную алгебру общими билинейными формами. Нужна отдельная проверка всех сокращений, использующих предположение о весе 1.

### Точная и символьная арифметика пока не является контрактом пакета

В алгебраическом конструкторе коэффициенты меньше `10⁻¹⁰` неявно удаляются. Поэтому `1e-12 * quForm([(a,b)])` превращается в нуль. Это не только погрешность печати: выражение теряет член. `SymPy Rational(1,3) * Point("a")` завершается `TypeError`; символьный коэффициент `t` в `Polyform` также не проходит сравнение с численным порогом. [Округление коэффициентов](https://github.com/magin67/polyform_algebra/blob/6e5da8dd14265ef67a0ed472344187ad28207317/polyform_algebra/_core/lincomb.py#L10), [скалярная арифметика](https://github.com/magin67/polyform_algebra/blob/6e5da8dd14265ef67a0ed472344187ad28207317/polyform_algebra/objects/element.py#L100).

Не следует называть текущий формальный слой точным лишь потому, что он манипулирует символическими именами точек. Для исследовательского эталона нужны явные домены коэффициентов и отсутствие приближённого удаления членов в точном режиме. Расширение поддержки SymPy должно проверяться отдельно; оно не возникает автоматически от добавления зависимости.

### Границы модели и терминология

Актуальная [спецификация PMG, редакция 27](https://github.com/magin67/pmg-notes/blob/9bbd84fe7a40292da6780bc4491f15ba2b3e318e/pmg-library/ru/%D0%9D%D0%B0%D1%87%D0%B0%D0%BB%D0%BE%20%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D1%8B%20%D0%B8%20%D0%BE%D1%81%D0%BD%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/%D0%9E%D1%81%D0%BD%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/%D0%A1%D0%BF%D0%B5%D1%86%D0%B8%D1%84%D0%B8%D0%BA%D0%B0%D1%86%D0%B8%D1%8F%20%D1%8F%D0%B4%D1%80%D0%B0%20PMG.md) описывает более широкую теорию форм, чем программный пакет. [Правила программного проекта](https://github.com/magin67/polyform_algebra/blob/6e5da8dd14265ef67a0ed472344187ad28207317/AGENTS.md) намеренно ограничивают публичную модель поддерживаемыми квадратичными формами. Это осознанная граница, а не основание немедленно реализовывать всю теорию.

Есть и терминологическое расхождение: в коде `Point` означает объект веса 1 без утверждения о метрике, а текущая спецификация называет точкой элемент нулевой нормы при выбранной метрике. `Element` в коде допускает произвольный вес. Для агента публичной библиотеки нужен явный словарь соответствий; иначе совпадение названия класса с термином заметки создаёт ложные выводы. [Контракт Point](https://github.com/magin67/polyform_algebra/blob/6e5da8dd14265ef67a0ed472344187ad28207317/polyform_algebra/objects/element.py#L134).

Дополнительные границы: плотный `float64`, отсутствие общей разреженной модели, незавершённые направленные метрические переходы и общие вырожденные проекции. Они частично уже корректно оговорены в [MATRIX_DEFERRED.md](https://github.com/magin67/polyform_algebra/blob/6e5da8dd14265ef67a0ed472344187ad28207317/docs/MATRIX_DEFERRED.md). Направленный лапласиан можно хранить и балансировать, но это не означает наличия полной направленной резистивной геометрии.

## Минимальное эталонное ядро PMG

Предлагаются пять групп возможностей. Названия функций ниже описывают целевой контракт, а не объявляют уже существующий API. Не требуется новая универсальная иерархия классов.

### Контекст и проверка входа

Одна общая модель конечной сети: устойчивые метки и порядок вершин, явные проводимости, изолированные вершины, тип графа, компоненты. Для матриц — роль, представление и пространство. Точный рациональный и численный режимы выбираются явно.

Постоянные функции: проверка сети, преобразование порядка, проверка L/Gr/R, проверка аффинного веса и принадлежности координат. Параллельные проводимости можно суммировать для метрических расчётов; при рёберной комбинаторике отдельные рёбра должны сохраняться. Нужна единая политика двух существующих импортёров.

### Матричные представления и сопротивления

Постоянные функции: `laplacian`, `green`, `resistance`, восстановление L из допустимой R, `spanning_tree_weight` через кофактор.

В связной точной модели гриниан можно получать стандартной линейной алгеброй из `Gr=(L+11ᵀ/n)⁻¹−11ᵀ/n`. Численный режим использует подходящий решатель и контроль невязки. Для нескольких пар достаточно заземлённых решений без полной обратной матрицы. Несвязность обрабатывается явно: компонентные гринианы, бесконечные межкомпонентные сопротивления и отсутствие глобальной нормировки на ненулевой остовной коэффициент.

Эти операции стандартны математически, но их **PMG-контракт** должен быть постоянным: веса являются проводимостями, R содержит квадраты евклидовых расстояний, малая ненулевая связь не превращается самопроизвольно в отсутствие связи.

### Метрическая оценка

Постоянные функции: скалярное произведение аффинных векторов `uᵀ Gr v`, матрица Грама, оценка простой структуры через определитель Грама, квадратичная норма и явная нормировка геометрического объёма.

Для границы k-симплекса квадрат геометрического объёма требует деления соответствующего определителя на `(k!)²`. Термины «норма» и «радиус» в PMG обозначают квадратичные величины; линейный корень должен быть отдельным результатом.

Для обычного сопротивления, площади, объёма или остовного веса **не нужно строить полную полиформную экспоненту**. Объём внешних координат растёт как биномиальный коэффициент, а полное перечисление лесов может быть очень большим. Экспонента оправданна, когда нужен именно формальный ответ по грейдам или независимая проверка.

### Граничные задачи и преобразования графа

Постоянные функции: `dirichlet`, гармоническое продолжение, `kron_reduce`, `contract`, `induced_subgraph`.

Это небольшой набор разных по смыслу операций. Исключение сохраняет резистивную метрику на оставленных вершинах; стягивание отождествляет вершины; индуцированный подграф удаляет связи. В задаче Дирихле каждая участвующая компонента должна иметь выбранную граничную вершину. Условия единственности и порядок меток входят в результат, а не остаются устной договорённостью.

Двудольное исключение можно оставить удобной оболочкой над этим набором. Геометрию сферы и остовную центральность — небольшими производными функциями, без новых решателей.

### Небольшой формальный слой

Сохранить проверенные внешнее произведение, границу, грейды, линейные комбинации, поддерживаемые квадратичные формы, их произведение, эквивалентность через раскрытие и конечную экспоненту. Потенциал и норма должны иметь явную область определения и фиксированную старшую форму.

Для внутреннего эталона достаточно координатных внешних структур с точными коэффициентами. Компактные записи границ служат удобным представлением, но не должны подменять общие правила там, где сокращения неприменимы. Результат вне поддерживаемой модели должен быть явной ошибкой/статусом, а не нулём.

Полные билинейные формы, произвольные поляризации высших грейдов, направленная геометрия, граничные паспорта и S/L/R-автоматы не входят в минимальный обязательный интерфейс. Их можно подключать как проверенные тематические расширения. Это сохраняет действующую границу программной алгебры.

### Обязательный эталонный корпус

Проверочные данные и независимые реализации являются частью поставляемого эталона, хотя не обязаны быть частью публичного вычислительного API. Минимальный набор должен включать:

1. Точные малые графы: взвешенный путь, треугольник, цикл, звезда, полный граф, изолят и несколько компонент.
2. Независимые сравнения: заземлённое решение ↔ гриниан; кофактор ↔ перебор остовов ↔ старший коэффициент; грамов определитель ↔ полиформная норма.
3. Алгебраические тождества: знаки, ассоциативность на поддерживаемом домене, `∂²=0`, Лейбниц, компактное раскрытие, нуль/единица, факториалы экспоненты.
4. Пограничные режимы: произвольные аффинные веса, малые и большие масштабы, перестановки меток, почти вырожденные системы, неправильные знаки, кратные собственные значения.
5. Отказы: неподдерживаемая направленная операция, неопределённая нормировка, неполная граница Дирихле и неизвестные символьные условия.

Тест должен фиксировать источник определения и его редакцию. Изменение терминологии заметки не должно незаметно менять смысл уже опубликованного вычислительного результата.

## Роль ИИ и дальнейшая организация

ИИ разумно поручать перевод вопроса в математическую постановку, выбор рецепта, сборку конкретного графа, использование SymPy, перебор малых примеров, графики и объяснение результата. Для нового исследования отдельный проверяемый скрипт часто эффективнее расширения API.

Эталонному ядру следует поручать операции, которые повторяются, имеют тонкие соглашения или должны одинаково работать у разных пользователей и агентов. Агент выбирает операции и объясняет ответ; библиотека проверяет входы, выполняет фиксированные преобразования и возвращает результат с условиями применимости.

Минимальная запись вычисления для агента: идентификатор операции и версия ядра, исходные метки/данные, режим арифметики, допуски, использованная редакция определения, результат и диагностический статус. Различать точный ответ, численную аппроксимацию, неподдерживаемую постановку и неразрешённый численный случай. Это полезнее, чем свободно исполняемый «универсальный PMG-код», заново генерируемый для каждого типового запроса.

Рекомендуемая последовательность последующей работы:

1. Зафиксировать поддерживаемую область и словарь между терминологией заметок и классами. Устранить две воспроизведённые ошибки, отделить точные коэффициенты от численного округления. Нынешние исходники в рамках этой ревизии оставлены без изменений.
2. Выбрать один путь сетевых преобразований и тонкие адаптеры к NetworkX/pandas. Сохранить существующие независимые проверки, добавить воспроизведения найденных пробелов.
3. Выделить пять описанных групп как стабильный контракт. Начать с рациональных эталонных входов; поддержку общих символов и больших разреженных задач вводить по реальным потребностям.
4. Настроить повторяемую проверку поддерживаемых версий, установки пакета и корпуса эталонов. После этого принимать решение о слиянии программной ветки и подключении агента.
5. Переносить функцию из исследования в тематическое расширение, когда есть повторное использование, устойчивое определение, ясный домен и независимый способ проверки. Новая заметка сама по себе не требует нового модуля.

**Рекомендуемое решение:** сохранить `polyform_algebra` как основу небольшого эталонного слоя PMG; приоритет отдать точности, условиям применимости и проверочным примерам. Новые исследования продолжать на Python/SymPy, не ставя их в зависимость от полноты пакета. Собственная реализация оправданна там, где она хранит устойчивый математический смысл и предотвращает повторяющиеся ошибки.
